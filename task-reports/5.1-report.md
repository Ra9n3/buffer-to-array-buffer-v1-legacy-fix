## Formats and validation behaviour (as built; `data-model.md` §12.2)

The rules are constants in `src/lib/audio/import-rules.ts` —
`ACCEPTED_SAMPLE_RATE = 48000`, `ACCEPTED_FORMATS = ["24-bit PCM", "32-bit
float"]`, `MAX_CHANNELS = 2` — and `judgeFormat()` applies them in order
(encoding → depth → rate → channels) to what `inspectWav()` found. The
format is judged **before any sample is read**. Nothing is converted.

## Storage and reopen behaviour (as built; §12.3, §12.5, §12.7)

- **One database per browser**, `alloy` v1, `assets` + `peaks`, keyed by
  `assetId` (`asset-<uuid>` from the platform's `crypto`, as project ids).
  `indexedDbAssetStore(indexedDB)` is created by the shell only
  (`const idb = win.indexedDB; return idb ? indexedDbAssetStore(idb) :
  null;`) and handed to `assets.attach()` before the lifecycle attaches;
  `unwire` detaches it after `lifecycle.detach()`. The pipeline and the
  tests run against the same `AssetStore` interface with
  `memoryAssetStore()`. No other module touches IndexedDB (guarded).
- **The pipeline** (`src/lib/project/import.ts`, pure of the browser):
  per file, in batch order — read → `inspectWav` → `judgeFormat` →
  `computePeaks` → `sha256Hex` → `store.put(asset, peaks)` →
  `createImportedTrack`; a failure at any step gives the file its line
  and **nothing else** (no record, no track). After the batch the
  accepted stems are appended **in one structural change**
  (`appendTracks(tracks, arrangement)`: 50 fields per track join the
  registry, the history is rebound) and their clips are set from the
  peaks just computed. The batch yields to the browser between files
  (`yieldBetween`, a macrotask injected by the shell) so the status line
  updates. 9 files / 12 MB took 822 ms in the evidence run.
- **Reopen** = the template rebuilt + the manifest's `tracks` appended
  (`withImportedTracks`; each `audio` validated by `isTrackAudio`; a
  duplicate id / code or a bad block makes the entry `damaged`) + the
  saved values (D4.1.1); `install()` ends with `void assets.hydrate()`,
  which clears the status map, reads each imported track's `PeaksRecord`
  (one at a time, abandoned if the project changes mid-way), checks its
  `sha256` against the track's, validates it, sets the clip and marks the
  track `ready` — or `missing`. **Verified with real files** (step 5):
  after a full reload the imported project is restored
  (`restored.outcome = "restored"`), all five tracks `ready`, five
  `audio` clips with path lengths identical to the ones drawn at import
  (3635 / 2775 / 3635 / 1722 / 93 characters). After deleting one
  asset's two records from the database and reloading (step 8): that
  track is `missing`, its row prints **MISSING**, its lane has no clip,
  the other four are `ready`, and the project opens normally.
- **No leakage** (steps 6–7): Start empty after the import → a new
  project with 0 tracks, no statuses, no clips, no report, the band
  present; opening the imported project again brings the five back
  `ready`; importing into the **fixture session** appends `21 pad` after
  the twenty fixture tracks (their clips stay `fixture` / SIMULATED, the
  tempo map and 56 bars stay, 1 126 fields), and the fixture reloads with
  track 21 `ready`. The copy's `projectId` is recorded (`session-fixture`
  vs `project-…` in the final database listing).
- **Not undoable**: an import is a structural change, not a field edit
  (D5.1.4). Removing an imported track or its copy is not in this build
  (approval item).

## Peak representation and calculation (as built; §12.4)

```
PeakData { schema: "alloy.peaks/1", sampleRate, frames, channels,
           perSecond: 50, framesPerBucket: 960, bucketCount: ceil(frames / 960),
           data: Int8Array[channels] of length 2 × bucketCount  — [min₀, max₀, min₁, max₁, …] in 1/127,
           channelPeak: number[], peak: number, nonFinite: number }
```

`computePeaks(bytes, format)` walks the data chunk through the 24-bit /
32-bit-float reader (`sampleReaderFor`) in slices of 480 000 frames,
keeping the signed min / max of every 960-frame bucket per channel —
**2 bytes per bucket per channel**, whatever the file's size: measured
2 400 B for each 12 s stereo stem, 930 B for the 9.3 s mono stem, 60 B
for the 0.3 s click (`peakBytes` in `import-5.1.json`); the tests put a
five-minute stereo stem at 60 kB against 115 MB of samples. The PCM is
never held beyond the slice; the stored copy is the file, not the samples.
The sample peak is kept unclamped (floats may exceed 1; the drawing clamps
at ±127). Non-finite float samples are counted and make the file
UNREADABLE. The peaks are stored under the asset's `sha256`; `hydrate()`
treats a record with another fingerprint as missing, so **a waveform never
shows for a copy that is not the imported file**. The lane draws
`peaksPath()` at 32 points a bar (the fixture's `WAVE_LAYOUT`), one path
per channel; the evidence lane of `kick.wav` shows its 24 transients
(two a second at 120 bpm for 12 s) with the right channel at 0.92 of the
left, as generated.

## Deviations, issues, limitations and approval items

**Deviations from the prompt / plan — none.** The formats are the plan's
list exactly (owner, D5.1.3); nothing wider was added.

**Limitations (documented, not blockers):**

1. **Mono is flagged, not yet duplicated** — "played on both sides" is the
   engine's job (5.2+); nothing plays in this build, so the flag and the
   stamp are what 5.1 delivers of plan §11's mono rule.
2. **Padding is a render-time comparison**, not written silence; the
   engine will pad at load. The PADDED stamp and the line identify the
   stems.
3. **No removal of an imported track or its copy**, no rename, no
   drag-and-drop, no undo of an import (D5.1.4). A copy stored during a
   batch whose project was switched mid-way stays in the database under
   the old project's id (D5.1.8) with no UI to remove it.
4. **One database per browser** (`alloy`): assets are bound to a project
   by the project's structure (its manifest's `tracks`), and the records
   carry `projectId`; nothing in this build lists or prunes assets.
5. **Home's template label** still prints "Empty project" for a project
   started empty that now has stems (the label is the template, as
   approved in 4.1) — see approval item 4.
6. **The report scrolls inside the band** past four lines (7.5 rem cap);
   with the problems first, a long batch's additions are below the fold
   until scrolled. The status line gives the count.
7. **Large files**: the whole file is read into memory once
   (`File.arrayBuffer()`) to hash and copy it; peaks are computed in
   slices. A multi-hundred-megabyte stem would hold that much memory for
   the duration of its own step only.
8. The Mixer / Console detail at 720 px tall: as in 4.1, the detail panel
   sits below the fold (unchanged rooms).

**Approval items (please decide):**

1. **Refusals first** in the report (D5.1.7) versus strict batch order.
2. **The validation vocabulary** — ADDED / REFUSED / UNREADABLE / FAILED;
   row stamps MONO / SILENT / PADDED / MISSING; the sentences in §12.2.
3. **Import not undoable** (D5.1.4), and the deferral of remove / rename
   of imported tracks and of asset pruning to a later task.
4. Whether Home should print something other than the template label for
   a started-empty project that now carries stems (e.g. the track count is

5. **The silent threshold −80 dBFS and "very short" < 1 s** — provisional
   constants until the engine (5.2) fixes its chunk size.
6. The imported track's defaults (D5.1.11): Supporting, `neutral` org, no
