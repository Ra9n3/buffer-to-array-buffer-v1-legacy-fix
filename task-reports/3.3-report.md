## History — boundaries, grouping, limits (as built; `data-model.md` §10.2)

| | Rule | Why |
|-|------|-----|
| **In history** | every registered field (10.1): channel settings, send slots, outputs, chain values **and** modes, identity classification (family, source, priority, tier confirmation) | they are the project data the approved UI edits; an identity change from Arrange must be undoable from the Mixer |
| **Never in history** | the Mixer's selection, scroll, open menus (component `$state`); fixture / presentation state (names, roles, display, notes, arrangement); `original` baselines; the clipboard's held payload; autosave status | they are not fields — the registry is the only thing history can see, so the exclusion is structural, not a filter |
| **Restores** | undo / redo write through the field setters with `applying` set; `observe()` returns null meanwhile | a restore is never a new edit; the baseline moves with the restore |
| **One entry =** | one synchronous block of writes (the observer runs after the block) — `setParamValue` (value + mode → Manual), `setTrackFamily` (+ source cleared), `setAllModes`, `chooseTrackTier` (priority + confirmation) are each one step | what the hand did once is one step |
| **Coalescing** | more writes to a **subset of the open entry's paths**, within **1 000 ms** of its last change, with a clock installed → merged (first `before`, latest `after`); a merge back to the start value drops the entry | a fader drag or a knob turn is one step; two different controls stay two steps; nothing coalesces across an undo, a transaction, a pause or without a clock (Node tests are deterministic) |
| **Transaction** | `history.transaction(label, fn)` — closes the previous entry, records the block as one closed, labelled entry (the store's paste) | a 37-setting paste is one step and cannot merge with the next adjustment |
| **Redo** | cleared by any new entry or merge | linear history; branching is not planned |
| **Limit** | 200 entries (`DEFAULT_HISTORY_LIMIT`), oldest dropped | an entry is a few patches (≤ 37 for a paste) — far under 100 kB at the limit; no UI navigates deeper yet; overridable |
| **No entry** | same-value writes, rejected routing writes, rejected / unchanged pastes, unknown-id throws | nothing moved → `observe()` finds no patch |
| **Cost** (Node, 2 000 iterations over the real store) | `observe()` 0.12 ms idle / 0.16 ms after a write; `undo()` 0.21 ms | vs 36 ms / 344 kB per snapshot in the rejected design |

Routing validity is preserved under undo / redo because the field setters
write the same references the validated ops wrote, in reverse order; the
editing tests assert `validateRouting().ok` after every restore and the
33-write round trip ends byte-identical.

## Autosave — mechanism, lifecycle, failure handling (`data-model.md` §10.3)

- **One mechanism, shared:** the store creates one `Autosave`; every history
  event (record, merge, undo, redo, clear) calls `notifyChange()`; the shell
  attaches `localStorage` + `setTimeout(…, 1000)`. Nothing else writes.
- **Lifecycle:** `clean` (nothing ever changed) → `dirty` + `pending` (timer
  armed; each new event re-arms) → `save()` → `saved` (`written`, or
  `unchanged` when the text equals the last saved text — e.g. an edit and its
  undo — then **no write**, `skipped++`) or `failed` (the adapter threw:
  `error` carries the message, `savedRevision` / `savedAt` / the stored text
  are untouched, the project stays `dirty`; the next change re-arms and a
  successful write clears the error; if the content returns to the stored
  copy the stored copy is current and the error clears without a write).
- **In-memory vs last-saved:** `revision` (history) vs `savedRevision`
  (autosave); `dirty` is their inequality; `status` also reports `pending`,
  `writes`, `skipped`, `error`, `savedAt`, `storage`, `key`.
- **No interference:** writes are synchronous, ~30 kB, after a 1 s quiet
  period, and only *read* the state through the registry; the rooms' sync is
  the same store objects as before. Measured in the browser: the write lands
  **1 001–1 059 ms** after the last history event; one write per burst; zero
  writes while idle.
- **Unavailable storage:** the `localStorage` lookup is in a try / catch; on
  failure nothing is attached and `status.storage` is `null` — the state can
  be `dirty`, never `saved`; `save()` answers `no-storage`.
- **Write-only (owner):** the app opens the fixture session on every load;
  `parseManifest` exists for tests and the load task; nothing applies a
  manifest. The manifest includes identity and routing fields so that a
  future load can reproduce the project.
- **Not persisted:** history, the clipboard, selection.

## Copy / paste — the exact copyable boundary and compatibility (`data-model.md` §10.4)

**Copied (copyable = true):** `channel/trim`, `channel/pan` (tracks) /
`channel/balance` (bus), `channel/level`, and every `chain/*` field —
`chain/eq/bypassed`, each band's `freq` / `gain` / `q` **value and mode**,
`chain/comp/bypassed`, `character` value and mode, `threshold` / `ratio` /
`attack` / `release` / `makeup` value and mode (tracks and the bus);
`chain/bypassed`, `character`, `time`, `second`, `tone` value and mode
(Returns). **Never copied:** `familyId`, `sourceTypeId`, `priority`,
`tierConfirmed`, `output`, `sends/<i>/{to, level, mode}`, `channel/mute`,
`channel/solo`; and nothing that is not a field (id, code, name, kind, type,
org, role, effect, `original`, loaded send levels, display, Return output).
The list is pinned by name in `tests/clipboard.test.mjs` (`TRACK_COPYABLE`)
and by the guard.

**Compatibility, decided before any write, in this order:** payload shape
(`malformed`) → destination exists (`unknown-destination`) → same kind
(`kind-mismatch`: track ↔ Return ↔ bus never paste) → same Return effect
(`effect-mismatch`: reverb ↔ delay) → every payload key is a copyable field
of the destination (`shape-mismatch`) → every value valid for its field
(`invalid-value`). Only then a plan of the differing fields, in registry
order; a plan of zero is `ok` with `changes: 0` and writes nothing. **No
partial modification** is possible: nothing is written until the whole
payload passed (tested: an out-of-range value in the last key leaves the
destination byte-identical). The destination keeps its identity, kind,
routing, send assignments, mute / solo, name; a Return keeps its identity
and its fixed Master output; the chain's structure cannot change (fields are
matched by `rel`; nothing is added or removed). Pasted parameters take the
source's **value and mode** (owner); the destination's `original` is
untouched, so return-to-Auto afterwards still only changes ownership (D2.8).
The store's `clipboard.paste` is **one history entry** and the rooms show it
at once (same bound objects). There is **no copy / paste UI** — the API is
`clipboard.copy(id)`, `clipboard.canPaste(id, payload?)`, `clipboard.paste
(id, payload?)`, `clipboard.held`, `clipboard.clear()`; in the browser it is
reachable through `window.alloy` with `?debug`.

## Key decisions and rationale

- **D3.3.1 — the owner's four decisions**, as applied: shortcuts only;
  `localStorage`, write-only, never restored; paste copies value **and**
  mode; `window.alloy` only behind `?debug`.
- **D3.3.2 — one registry, diff history, one observer** (not snapshots —
  344 kB / 36 ms each in the experiment; not instrumented ops — 23 ops plus
  the 2.8 helpers plus direct component writes would all need touching).
  The observer makes the write paths unchanged and the boundaries structural.
- **D3.3.3 — the manifest is the registry; autosave never lies**: saved
  point moves only on success; unchanged text is skipped; storage injected.
- **D3.3.4 — validate the whole payload, then write in registry order, as
  one transaction**; verdicts with reason codes and sentences (the 3.2
  pattern) as the API for a future Edit action.
- **D3.3.5 — one shell**; the decisions are pure functions; text-entry
  exemption keeps the browser's own undo in a field being typed in.
- **D3.3.6 / D3.3.7 — tests and guards** (below).

### Where the documents are silent (assumptions — please correct any)

- **Coalescing window 1 000 ms and limit 200** — the plan names neither;
  both are constants with a documented rationale and overridable.
- **Identity classification (family, source, priority, tier) is in
  history** — the plan's "every edit" read; undoing an Arrange
  classification from the Mixer is therefore possible.
- **The manifest includes identity and routing** (not only the copyable
  settings) so a load can reproduce the project; it carries no timestamp.
- **Ctrl + Y is redo only with Ctrl (not Cmd), no Shift** — the Windows
  convention; on macOS Cmd + Shift + Z is the redo.
- **A paste onto itself / an identical channel is "Unchanged" and `ok`** —
  the 3.2 "Unchanged is ok" reading.
- **Label wording** (`"03 Snare Bottom · level"`, `"… · 2 settings"`,
  `"Paste settings → …"`) and the rejection sentences are first drafts for a
  future Edit menu; cheap to change.

## Deviations, issues, limitations and approval items

- **No visible undo / redo control, no copy / paste UI, no autosave
  indicator — by owner decision and by the prompt.** Failures are
  *surfaced* through `autosave.status` (`failed` + `error`) and nothing
  ever says "saved" falsely; a visible save-state print and an Edit menu are
  later UI tasks over these APIs. Copy / paste in the browser is reachable
  only through `window.alloy` with `?debug`.
- **Write-only persistence** (owner): the manifest is written, never read
  back; a reload opens the fixture session (measured §I). Loading, "open
  project", multi-project and cloud are out of scope and not started.
- **History is per page load**: a reload clears it (not persisted — by
  design; the manifest has no history).
- **Approval items:** coalescing window **1 000 ms**; history limit **200**;
  identity classification in history; the manifest carrying identity and
  routing; the label and rejection sentence wording; Ctrl + Y (Ctrl only)
  as redo.

  focus, Ctrl + Z is left to the browser (text-entry exemption, tested in
  Node with the input types); not walked in the browser.
- **Fixture limits:** one bus, so bus ↔ bus paste compatibility and bus
  routing undo are proven in Node only (`setBusOutput` to Master is

- **`history.clear()` is API only** (a future "new project").
- **Guard pins** for all 3.3 files are "as reviewed" — any change on review
