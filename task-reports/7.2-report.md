## 3. How the sidechain signal path works

```
 track source ── input ─┬─────────────► its own chain ──► pan/fader ──► output/sends
                        │
                        └─ × TRIM ──► KEY BUFFER ──► destination's detector
                                                    (compressor / dynamic EQ)
```

The key is the source track's **input block × TRIM**, computed at the top of every block
before any chain runs. It is never summed into a bus, never sent to a Return, never
added to another channel: it exists only to be *listened to*.

`SidechainEdge` says `{ source: TrackId, destination: ChannelId, processor }`, so one
track can key several destinations and each detector is keyed independently. The audible
graph (`routingEdges`, `validateGraph`, summing) is untouched.

## 4. How external keys reach the two detectors

- **Compressor:** `process(input, output, count, key?)`, and the detector reads
  `key ?? input`. With a key, gain reduction is driven by the key while the compressor
  still multiplies **its own input** by the resulting gain. Without one, behaviour is
  bit-identical to 6.2.
- **Dynamic EQ:** unchanged from 6.1 — it already used `key ?? input` for the band
  detector, and the bands still filter the module's own audio.
- **Chains:** `TrackChain.process(buffer, frames, keys)` passes `keys?.dynamicEq` and
  `keys?.compressor`; `BusChain` passes `keys?.compressor` only (a bus has no dynamic EQ).
  An absent key is self-detection, by omission rather than by a mode flag.

## 5. Synchronisation and block boundaries

Because the tap is the source's **input**, the engine needs no cross-channel ordering:

- **Block-aligned by construction.** Keys are filled from the same block's inputs, before
  the chains run, so key and main signal describe the same frames. The test asserts the
  key acts inside the block it arrives in.
- **No stale buffers.** Every key buffer is written from scratch each block — copied when
  the source is present and audible, otherwise **zeroed**. A test removes the source from
  a block and asserts the reduction collapses immediately instead of replaying the
  previous key.
- **State continuity.** Compressor and dynamic-EQ envelopes live in their modules and
  carry across blocks; chunked processing with a sidechain is asserted sample-identical
  to a single pass.
- **No added latency.** The detector tap is not in the audible path;
  `latencyFrames` remains the limiter's 240 frames at 48 kHz, asserted with a sidechain
  present.
- **No allocation in the block loop.** Buffers are sized once from `maxFramesPerBlock`;
  the bundle object handed to each chain is reused every block. Asserted by a test and by
  the guard.
- **Cycles are structurally impossible.** A key never depends on another chain's output,
  so A↔B keying is well defined and needs no ordering rule; only a self-key is rejected.

## 6. Routing validation and cycle handling

`validateSidechains()` is separate from `validateGraph()` and, unlike it, **never throws**:
a broken detector edge must not stop a project from playing. Rejected edges are dropped
with a named reason and a message, and the processor falls back to its own input.

| Reason | Test |
| --- | --- |
| `malformed` | shape check |
| `unknown-source` | ✅ test + engine fallback |
| `unknown-destination` | ✅ test |
| `unsupported-destination` (Return) | ✅ test |
| `self-sidechain` | ✅ test + engine fallback |
| `duplicate-assignment` (first wins) | ✅ test |

`sidechainVerdict.ok` and `.problems` expose the result; nothing is silently connected.

## 9. Limitations and required future changes

1. **Store / UI / persistence are not wired.** `Project.sidechains` exists in the model and
   the engine, but the store does not edit it, the clipboard does not copy it and the
   manifest does not persist it. Assignments are therefore built by whoever constructs the
   `Project`, or through `engine.refreshSidechains(edges)`. Wiring it needs the clipboard /
   persistence contract extended for a new field — a deliberate, separate change.
2. **The tap is fixed at pre-fader/post-trim.** There is no post-fader or post-EQ key and no
   key-level control; adding one is a new approved control, not a silent extension.
3. **Destinations are tracks and buses; sources are tracks.** Return destinations and
   bus/Return sources are rejected by design (D7.2.5).
4. **No key filtering, weighting or lookahead.** The detector hears the key as-is, on the
   module's own approved detector and timing.
5. **Multiple keys per destination are one per processor.** A destination's compressor can
   have exactly one key; so can its dynamic EQ.
6. **Out of scope by instruction:** masking (7.3), rendering/tail handling (7.4), playback
   and export.

- **One approved DSP file was edited** (`compressor.ts`): the task assumed it already
  accepted a key. The edit is the smallest one that satisfies the requirement, it does not
  change the algorithm, and it was approved in advance (D7.2.1). Recorded here because the

- **The model gained a field** (`Project.sidechains`), which the task excludes "without
  reporting the required contract first". It was reported and approved (D7.2.2); §9.1
  states what remains unwired.
- **Keys are silence, not bypass**, when the source is muted or solo-excluded: the
  detector keeps running with nothing to hear (D7.2.4). This is the owner's choice, not an
  inference.
- Everything else follows the task as written: no new DSP algorithms, no new detector
  modes, no UI, no changes to 7.1's pan/summing/solo/mute/Master behaviour.
