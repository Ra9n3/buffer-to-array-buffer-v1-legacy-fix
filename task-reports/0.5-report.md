One integrated Task 0.5. Three things were built, in the order the prompt lists
them:

1. **Top navigation adjusted.** The tabs moved from the centre of the top bar to

   ALLOY wordmark stayed on the left. No new routes or room identities.

   23 selectable placeholder channels on the left (20 tracks, then the Reverb and
   Delay Returns and the bus master) and a selected-channel processing-detail

   just in CSS: row height, padding, label alignment, typography scale, border

Selection is local per-room UI state in `$state`: no store, no persistence, no
cross-room synchronisation. Strips are real `<button>` elements with
`aria-pressed`, so mouse and keyboard both work.

No audio, DSP, routing, waveforms, playback, project state, design tokens, or
Phase 1/2 visual styling were added. Task 0.6 was not started. Arrange and Console were not modified.

## Header parity with Arrange — how it was matched

The requirement was that the Mixer headers match the Arrange headers in row
height, dimensions, padding, label alignment, typography and border treatment.
The approach was to make the shared values a single declared source of truth
rather than copying numbers into a second file:

- `app.css` now declares `--track-header-height: 5rem`,
  `--track-column-width: clamp(10rem, 16vw, 15rem)`,
  `--track-header-padding-block: 0.25rem`,
  `--track-header-padding-inline: 0.5rem`,
  `--track-header-gap: 0.375rem`,
  `--track-header-code-size: 0.6875rem`,
  `--track-header-name-size: 0.875rem`. A 40rem media query mirrors Arrange's
  own compact values.
- `MixerChannelStrip.svelte` consumes those tokens for height, padding, gap and
  both font sizes, and reproduces the Arrange row's identity line: baseline-
  aligned monospace code at 700 weight in #5d5d5d, then the 600-weight name with
  ellipsis overflow.
- `ArrangeTrackRow.svelte` was **not** edited. It keeps its own literals
  (`--arrange-row-height`, `0.25rem 0.5rem`, 0.6875rem, 0.875rem, 0.375rem,
  #ececec, 2px #8a8a8a right border, 1px #d0d0d0 bottom border).
- `npm run check:mixer` asserts the two representations agree: it reads the
  `--track-header-*` values out of `app.css`, asserts each is still a `var()` in
  the Mixer strip, and asserts each equals the literal value still present in
  `ArrangeTrackRow.svelte`. Change either side alone and the check fails.

One geometry trap had to be solved: the channel column originally drew its frame
as a 2px border, which made every Mixer header **236px** wide at 1920 against
Arrange's **240px**. The column frame is now an inset `outline`, which costs no
layout width, and the widths match exactly at every viewport.

### Measured in the running app (not just CSS)

| Property | Arrange row | Mixer strip | Match |
| --- | --- | --- | --- |
| Height @1920×1080 | 80px | 80px | ✅ |
| Width @1920×1080 | 240px | 240px | ✅ |
| Height/width @1024×768 | 80 / 163.8px | 80 / 163.8px | ✅ |
| Height/width @768×900 | 80 / 160px | 80 / 160px | ✅ |
| Padding | `4px 8px 4px 8px` | `4px 8px 4px 8px` | ✅ |
| Border right / bottom | `2px solid rgb(138,138,138)` / `1px solid rgb(208,208,208)` | identical | ✅ |
| Identity gap | 6px | 6px | ✅ |
| Code text | 11px / 700 / rgb(93,93,93) | identical | ✅ |
| Name text | 14px / 600 / 16.8px line-height | identical | ✅ |
| Background (unselected) | rgb(236,236,236) | rgb(236,236,236) | ✅ |

The selected state does **not** change dimensions: measured selected and
unselected strips are both 80×240. Selection is expressed as a background change
to #dcdcdc plus an inset `box-shadow` ring (3px left bar + 2px outline), so no
box metric moves. `check:mixer` fails if `height`, `width`, `padding` or
`border-width` is ever added to the selected rule.

The detail panel cannot force the headers to stretch: the column and the panel
are separate grid tracks, and the strip height is a fixed token rather than a
stretch value.

## Viewports actually inspected

Real browser, `page.setViewportSize` then a full reload, at each size:

| Viewport | Mixer page fits | Mixer detail overflow | Arrange row | Arrange drift | Console intact |
| --- | --- | --- | --- | --- | --- |
| **1920×1080** | ✅ no page scroll | 0px | 80×240 | 0px | 23 strips, 3 zones |
| **1024×768** | ✅ no page scroll | 0px | 80×163.8 | 0px | 23 strips, 3 zones |
| **768×900** | ✅ no page scroll | 0px | 80×160 | 0px | 23 strips, 3 zones |

Screenshots were taken and visually inspected at 1568×713 for all three rooms,
and at 1024×768 and 768×900 for the Mixer. Visual findings that the numbers did
not show, and which were fixed:

1. The Mixer detail panel was rendering at roughly half width, leaving a dead
   area to its right — the panel did not stretch inside its flex host.
2. At 1568×713 the chain labels truncated to `Input tri…`, `Static m…`, and each
   row repeated a `Placeholder` tag. The per-row tag was replaced with one
   explanatory line and the columns widened; labels now read in full.
3. At 1024×768 the five detail blocks fell into a 4 + 1 wrap, leaving two empty
   grid cells. The minimum column width is now 9rem, so they sit on one row.
4. The detail pane left a large empty band below the last block. The grid now
   grows to fill the pane instead of leaving dead space.

Known cosmetic limit, reported rather than hidden: at 713px viewport height the
channel column shows about 6½ of 23 strips, with a partially clipped strip at the
bottom edge. That sliver is what signals "this scrolls", the same convention the
Console bank uses on its right edge, but it is a deliberate choice and the owner
may prefer a fade or an explicit row count instead.

## Deviations, decisions, and items for owner input

1. **Tab order vs. plan §14.** The plan lists the rooms as "Console/Arrange/
   Mixer"; the tabs now read Arrange, Console, Mixer because the owner specified
   it. Recorded in a comment in `rooms.ts`. The default landing room is still
   Console.

2. **Channel-type branching deferred.** Plan §3 states the Mixer detail panel
   *must* render differently per channel type, and §14 schedules that as Task
   2.9. Per this task's exclusion list, the panel shows one neutral placeholder
   layout for every channel type, including Returns. `check:mixer` guards that no
   `channel.kind ===` branching appears early. Flagged as an open conflict between
   "the plan is the source of truth" and "do not implement 2.9's branching"; I
   followed the task prompt's exclusion and am recording it rather than deciding
   it.

3. **Prominence Tier / instrument combobox not present.** Plan §2.7 puts the
   Prominence Tier switch and instrument-name combobox on the Mixer strip. Those
   are Phase 2 controls and were deliberately not added in Phase 0.

4. **Arrange's own literals were left alone.** The cleanest single source of
   truth would be to change `ArrangeTrackRow` to consume the same tokens. The
   prompt forbids changing Arrange, so instead the tokens are declared in
   `app.css` and the check script enforces equality with Arrange's literals. The
   cost is one duplicated set of numbers plus a guard; the benefit is that
   Arrange is untouched.

5. **One shared file did change.** `app.css` and `rooms.ts` are global, so
   reordering the tabs and adding tokens necessarily touches files Arrange and
   Console also read. No room-local Arrange or Console file was edited.

6. **`DEFAULT_ROOM` deliberately unchanged** (still Console), so first load
   behaves as it did before this task.

7. **Bus master label.** Plan §8a defines Return buses precisely but is silent on
   whether there is exactly one bus master; the placeholder keeps the single
   "Bus master" channel the Console bank already uses, for cross-room consistency
   rather than a new product decision.
