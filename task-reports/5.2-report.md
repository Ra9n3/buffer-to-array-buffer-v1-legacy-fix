## The engine, as built (`data-model.md` §13.1–§13.3)

**One pass, one grid.** `Analyser` (`analyser.ts`) accumulates per 100 ms
cell (`CELL_SECONDS 0.1` = 4 800 frames): the peak and the sum of squares
per channel, the K-weighted power, the true-peak maximum, Σ L·R / Σ L² /
Σ R², the spectral frames whose centre falls in the cell, the transient
blocks, the integrity counters. `finish()` derives everything else. Every
component streams: the K-weighting biquads and the true-peak interpolator
carry their tails, the spectral analyser its partial frame, the transient
analyser its partial block and last onset. `analyse.ts` drives it:
`analyseSource(source, { sliceFrames, yieldBetween, signal, onProgress })`
reads `sliceFrames` at a time (the profile's `sliceSeconds` × 48 000;
`DEFAULT_SLICE_SECONDS 5`), decodes with Task 5.1's sample readers, pushes,
yields, reports, and throws `AnalysisAborted` when the signal flips.
`decode.ts` turns a stored Blob into a `ByteSource` and reads the header
out of the first 64 kB — `readWavHeader` / `inspectWav` gained an optional
`totalBytes` so chunk sizes are judged against the file, not the head
(the Task 5.1 call sites are unchanged; test added).

**What each category measures, and what the tests hold** — in
`data-model.md` §13.3 in full. The things worth the owner's eye:

- *True peak:* 4× oversampling with a Blackman-windowed sinc in four phases
  of 12 taps, each normalised to unit DC gain. The phases sit between the
  samples (±1/8, ±3/8), so the detector also takes the sample itself — a
  true-peak reading is **never below the sample peak**. (The first browser
  run showed the Task 5.1 click, a lone full-scale sample, at −0.24 dBTP
  against a 0.00 dBFS sample peak — physically impossible; fixed, with a
  regression. The 12 kHz tone sampled at 45° still reads its ≈ 3 dB of
  inter-sample peak within 0.25 dB.)
- *Loudness:* the published K-weighting (+0.69 dB at 1 kHz — the reason
  for the −0.691 offset), gates and windows per BS.1770-4, LRA per EBU
  Tech 3342. A mono stem counts on both sides (it plays duplicated,
  D5.1.3): +3 dB over the same signal in one channel of a stereo file.
- *Spectral:* the **mid** signal's spectrum — one FFT per frame pair and
  what a listener hears in mono; anti-phase content therefore has none,
  which the stereo figures (mono loss −∞ / correlation −1) say explicitly.
  The band *means* average the cells whose frames carry energy, judged on
  the frames themselves rather than on the level series. (The first
  browser run showed the click with every band mean null: its one sample
  at 0.1 s lands in a frame centred in the cell *before* it, which is
  silent by level. Fixed, with a regression; the kick's upper-band means
  rose by 30–60 dB in the process — the attack frames at its hits'
  cell boundaries had been dropped the same way.)
- *Transient:* a steady tone that starts at t = 0 has one onset (its
  start) — the engine says what it measured; a dB-linear fade-in has none.
- *Integrity:* clipping is three or more consecutive full-scale samples
  **of the same sign** (a full-scale square wave is clipped, a sine that
  touches 0 dBFS is not, a float stem over 1.0 is); DC offsets below the
  24-bit noise floor are "none", not −200-odd dBFS; silence keeps the 5.1
  rule and is measured but flagged *not a target*.
- *Edge cases:* digital silence · a mono float stem · a 0.3 s click · a
  left-only stem · anti-phase · a copy that is missing, swapped, truncated
  or not a WAV — all held by test, the first three also measured in the
  browser on the real files.

## Storage, the queue and the lifecycle, as built (§13.4, §13.6)

`asset-store.ts`: `ASSET_DB_VERSION 2`, `ANALYSIS_STORE "analysis"`; the
memory store (tests) and the IndexedDB store implement `putAnalysis` /
`getAnalysis`, and `remove` deletes all three records. `analysis.svelte.ts`
is the queue described in the summary; it is attached by the shell with
`{ now, clock: () => win.performance.now(), yieldBetween }` and the
asset store, detached in `uninstall()` in the order `lifecycle → analysis
→ assets → hardware → settings`. `assets.svelte.ts` gained the optional
`afterImport(ids)` hook; `lifecycle.ts`'s `install()` ends
`void assets.hydrate(); void analysis.hydrate();`. `hydrate()` awaits the
store one record at a time and checks the project id after each, so a
switch mid-way stops cleanly; `enqueue` skips what is ready, queued or
running; the worker's generation + signal drop an aborted run's result
and never write it under the next project (tests). A refused write keeps
the result for the session with `stored: false` and the reason.

## The hardware profile and the estimate, as built (§13.5)

`hardware.svelte.ts` is attached by the shell with `{ storage: adapter,
now, nowMs, clock, cores, memoryGb, yieldBetween }`, `cores` / `memoryGb`
from `navigator.hardwareConcurrency` / `deviceMemory` read in the shell
only (null where not reported). It reads `alloy.benchmark` once through
`parseBenchmark`; the queue calls `ensure()` before the first stem it
actually analyses — **after the copy is known to exist**, so a missing
stem never costs a measurement (found by the browser evidence: the first
run spent a benchmark on a deleted copy; reordered, with a test). The
profile resolves Settings → benchmark → Standard. `estimateSeconds(work)`
and `analysis.estimate { workSeconds, seconds, profile, basis }` sum the
queue, the running stem by its remaining fraction. The shell test holds
"no measurement, no estimate" and the debug keys.

## Deviations, issues, limitations and approval items

**Deviations from the template / the task prompt**

1. `architecture.md` and `module-contract.md`, which the task template
   names as reading, do not exist in the repository (as noted in 5.1).
   `data-model.md` and `decisions-log.md` carry the contract; §13 was
   written to serve as the module contract for the engine, the record,
   the storage, the queue and the profile.
2. Three engine / queue corrections were made **after** the first browser
   run, each with a regression test, and the evidence was re-run on the
   final build: the true peak never below the sample peak (D5.2.6), the
   band means judged on the frames (D5.2.7), the benchmark after the copy
   check (D5.2.2). They are listed here because the node tests did not
   catch them — the real files did.

**Limitations (by design, in this task)**

3. The pass runs on the main thread with macrotask yields; no Worker
   (D5.2.10). Measured cost ≈ 20–100 ms between yields at this machine's
   throughput; a 5-minute stem at 35× is ≈ 9 s of background work in 60
   slices under Standard.
4. The spectrum, the transients and the band balance are the **mid**
   signal's; no per-channel or side spectrum (D5.2.7). The stereo figures
   cover the image.
5. The true-peak interpolator is 4 × 12 taps (BS.1770-4 Annex 2 suggests
   a 48-tap 4× filter): ±0.25 dB on the worst-case inter-sample test, never
   below the sample peak. Good for a measure and a flag; an upgrade is an
   `ENGINE_VERSION` bump.
6. `navigator.deviceMemory` is Chromium-only and coarse; where a browser
   reports neither cores nor memory the Performance rule binds on
   throughput alone. The cache is keyed to the engine version and the
   core count, not to the browser build.
7. A Settings override applies from the **next** stem; the stem running
   finishes under the profile it started with (the figures are the same
   either way).
8. No room reads a result and nothing visible says that analysis ran —
   the task allowed no UI; the import band's lines, the Console's
   PROCESSING fixture and Home are as in 5.1. `window.alloy.analysis` /
   `window.alloy.hardware` (`?debug`) expose everything.
9. Records of removed assets are not pruned (Task 5.1's open asset
   lifecycle); re-analysis overwrites in place.

**Approval items (the owner's word is asked on each)**

- **A1 — the provisional thresholds:** profile < 25× / ≥ 100× with ≥ 4
  cores and ≥ 4 GB; estimate margin 1.25; onset 6 dB / −60 dBFS / 50 ms;
  near-silence −60 dBFS. All in one constant each, documented as
  provisional (D5.2.5, D5.2.8, D5.2.9) — to be tuned on real devices and
  stems; approve as the starting values or name others. (Measured
  illustration: the Task 5.1 pad, a slow swell of detuned layers, counts

- **A3 — silent stems are measured, flagged `analysisTarget: false`**
