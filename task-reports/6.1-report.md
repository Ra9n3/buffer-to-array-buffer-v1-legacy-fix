## Implementation summary

**One design, shared by both modules.** `bandCoefficients` is the RBJ
audio-EQ cookbook prototype at the session rate — `A = 10^(gain/40)`,
`ω₀ = 2πf/fs`, shelves at slope `S = 1` — stored normalised as
`[b0, b1, b2, a1, a2]`. It is the same arithmetic `mixer-chain.ts` draws the
Mixer's response graph from, and the EQ suite proves it: an impulse through
the module is transformed by a direct DFT at eight frequencies and compared
with `eqResponseDb` (the graph's own function) **within 0.05 dB**. A 0 dB
band is set to the exact identity, so a neutral band is transparent bit for
bit rather than by cancellation.

**`BiquadSection`** is transposed direct form II with carried state — the
analysis engine's `Biquad` arithmetic (§13), so the two runners agree — with
two entry points: `process` for a block (the Custom EQ) and `step` for a
sample (the Dynamic EQ, whose gain moves between samples). Both read the
same five coefficients and the same two state variables.

**The Custom EQ** builds one section per channel per band in the
constructor, copies the input to the output, then runs the bands in order in
place. Bypassed, it stops after the copy. `responseDbAt` sums the bands'
`magnitudeDb` — the settings drawn, never a signal measured — and is 0 dB
while bypassed.

**The Dynamic EQ**, per band and per sample: the band-limited detector
filter (one per channel) → the loudest channel's squared sample → a one-pole
envelope in the power domain (attack when the power rises, release when it
falls) → `envelope >= 10^(threshold/10)` → a 0/1 target → a 2 ms slew on
the indicator → `gain = staticGain − blend × depth` → redesign the section
if the gain has moved 0.01 dB → `step` each channel. The reduction reading
is `blend × depth`, exact.

## Important DSP decisions and rationale

| # | decision | why |
| --- | --- | --- |
| 1 | **Self-detection, or a key when supplied** (owner) | The plan describes the intermittent-masking case as a "sidechain-triggered dynamic EQ dip"; a dynamic EQ that can only sidechain is not the "tonal control" use the same block names. One module, both uses, no invented routing. |
| 2 | **Band-limited peak-power detector; the chain's THRESH / ATTACK / RELEASE** (owner) | The task asks for a "frequency-selective" module, so the detector must not be full-band. No document gives this block its own threshold or times; the project has exactly one set of dynamics ranges (D2.8.3) and a second set would be invented twice over. |
| 3 | **Full depth above the threshold, 0–15 dB, downward only** (owner) | The model says "pulled down"; the fixtures use 2–4 dB. Downward-only means a dynamic band can never add energy, which is what "yield space" means. |
| 4 | **The detector reads the band's own band, not the full key** | A bell's range is its band-pass at FREQ/Q; a shelf has no band, so it listens on its own side of the corner (low- or high-pass, Q = √½). Provisional, but the closest thing a shelf has to a band. |
| 5 | **The detector is linked across channels by peak** | One transient on one side must not move the image; the loudest channel's power drives one gain for the pair. The filter state stays per channel. |
| 6 | **A 2 ms slew on the indicator** (`DETECTOR_SWITCH_SLEW_MS`, provisional) | A binary law on a smoothed envelope is a **step** at the crossing — up to 15 dB, a click, and plan §11 forbids clicks at chunk edges and in general. 2 ms turns it into a ramp and leaves the documented attack dominant. |
| 7 | **Per-sample redesign, gated at 0.01 dB** (`GAIN_REDESIGN_STEP_DB`, provisional) | The gain is then exactly `gain − blend × depth` in dB (no approximate blend), the coefficients are continuous with the gain, and a steady band costs one comparison per sample instead of trigonometry. 0.01 dB is far below audibility. |
| 8 | **No allocation, no block-boundary branch** | Plan §11's chunked render (7.4) and the low-spec machines it protects: state is per sample, so one pass and any chunking give **bit-identical** samples — held by both suites (blocks of 1, 7, mixed, 1 000). |
| 9 | **A band belongs to exactly one module** | Block 3 and block 4 must not filter the same band twice: the static bands go to `Eq`, the bands that carry a depth to `DynamicEq` (a `depthDb: 0` band there is bit-identical to the static one). This keeps the two modules independent, as the task requires, and leaves 7.1 to assemble them. |
| 10 | **Ranges in one file, and the validation rule split the way the console already splits it** | Non-finite = caller bug = throw; finite out of range = clamp, like `fromPosition` / `setParamValue`. The provisional numbers are one constant each (D5.2.5 / D5.2.8's convention) so a tuning task moves them in one place. |
| 11 | **Settings are fixed at construction; bypass is a setting, not a switch** | A render snapshots the chain (plan §10), which is what makes the output deterministic. No mid-stream reconfiguration is offered that the renderer does not need. |

## Deviations, limitations and approval items

**Deviations from the template / the brief**

1. `architecture.md` and `module-contract.md` do not exist (never have);
   `data-model.md` §14 is the module contract for this task, as §13 was for
   5.2.
2. Two unrelated guard files were amended, both minimally and both because
   the test list changed: `check-editing-structure.mjs` (the exact
   `npm test` string) and `check-analysis-structure.mjs` (one regex that had
   assumed `benchmark.test.mjs` was the last suite). Details above.
3. The decisions log was **not** edited, per the brief, so the three owner
   answers and the provisional constants live in `data-model.md` §14.5 and
   here. The log entry is the owner's when this is approved.

**Limitations (by design or provisional, in this task)**

4. The dynamic detector's ranges reuse the **compressor's** documented specs
   (D2.8.3) because no document gives the dynamic block its own. If the
   owner wants, say, a longer release range for a dynamic band, it is one
   constant.
5. `DETECTOR_SWITCH_SLEW_MS 2` and `GAIN_REDESIGN_STEP_DB 0.01` are this
   task's numbers, provisional, and named as such in the source and §14.
6. A shelf's detector is one-sided at its corner (a 12 dB/octave slope), so a
   very loud low tone can move a high shelf's detector a few octaves away.
   Measured: at 800 Hz, a 200 Hz key at −1 dBFS triggers it, a 50 Hz key does
   not. Defensible ("listen on your own side"), but it is a choice a later
   listening test may revise.
7. The attack is the **detector's**; the gain's own move adds the 2 ms slew,
   so an attack faster than that is limited by the slew. Measured at 0.1 ms:
   the dip still arrives in about 2–3 ms.
8. `Eq` re-copies `input` to `output` on every call even when the bands are
   neutral; a render that already owns the buffer can pass the same array and
   the copy is skipped. Not optimised further because nothing measured it.
9. Non-finite **samples** are assumed absent — sanitising belongs at decode
   (Task 5.1 / 5.2 count them). A NaN in would poison a filter's state until
   `reset`, which is documented rather than silently papered over.
10. The modules take settings; they never choose them. No frequency, gain,
    depth or threshold is recommended anywhere — that is the rulebook's and
    7.3's work.
11. No browser evidence: the task allows no UI, and the modules are not in
    the bundle. If the owner wants a listening check now, a small dev route
    would be new scope.
