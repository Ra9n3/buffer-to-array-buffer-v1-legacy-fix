   product plan (Intro, Verse, Pre-Chorus, Chorus, Bridge, Solo, Outro).

6. **Organizational groups & bus-routing placeholder** — a separate region

live in a **single CSS grid whose rows are shared**, so a track row and its lane
are the same grid row. They cannot become misaligned, and there is no second
vertical scrollbar to desynchronise. See "Scrolling and alignment approach".

## Scrolling and alignment approach used

This is the correction the brief cares about most, so it is stated explicitly.

- **One scroller.** A single element (`[data-arrange-scroll]`, `overflow: auto`)
  owns both axes. There is no second vertical scrollbar anywhere in the room,
  so the track list and the timeline cannot desynchronise — there is nothing to
  synchronise.
- **Shared grid rows.** Inside the scroller, `.arrange-grid` is a CSS grid with
  two columns (`--arrange-track-list-width` for the track list,
  `--arrange-timeline-width` for the timeline) and `grid-auto-rows:
  var(--arrange-row-height)`. The `{#each}` emits the track row and the lane as
  consecutive grid items, so **row *n* and lane *n* are the same grid row**.
  Alignment is a property of the grid, not of two lists kept in step by
  JavaScript, and it survives font loading, resizing, and any row-height change.
- **Vertical scrolling moves rows and lanes together**, by construction.
- **Horizontal scrolling moves only the timeline.** The track-list column is
  `position: sticky; left: 0`, so the track cells stay pinned to the left edge
  while the lanes scroll beneath them. The timeline header shares the lane
  column and therefore scrolls with the lanes.
- **Headers stay put.** The track-list header is `sticky` on both top and left
  (it is the grid's corner cell); the timeline header is `sticky` on top. Both
  sit above the row content via `z-index`, so rows scroll *under* them rather
  than overlapping or displacing them.
- **The room is bounded to the viewport.** `.arrange-room` is
  `height: clamp(22rem, calc(100dvh - 13.75rem), 72rem)`, so the track list
  scrolls inside its own region instead of stretching the page. Without this the
  room grew past the fold and vertical scrolling fell back to page-level scroll,
  which is the mechanism that lets a track list and a timeline drift apart.
- **No hidden overflow as a workaround.** Nothing is clipped away to hide the
  problem: the scroller is a real, keyboard-focusable `role="region"` with a
  visible `tabindex` and `aria-label`, and every one of the 20 rows is reachable.

Row height (`--arrange-row-height: 2.75rem` desktop, `2.5rem` below 40rem) is
shared by `ArrangeTrackRow` and `ArrangeTimelineLane`, so the two cells cannot
disagree.

### Decisions and ambiguity

All three items flagged for the owner have been resolved. The resolutions are
recorded in "Owner resolutions (post-review)" below; this list is kept in its
original form so the decision trail is intact.

1. **Plan vs brief on independent scrolling.** The roadmap's review line reads
   "track list scrolls vertically independently of the timeline header", which
   could be read as asking for two separate scroll containers. That reading
   conflicts with the plan's own intent and produces exactly the drift defect
   the correction brief forbids. Implemented interpretation: **the row area
   scrolls vertically while the timeline *header* (structure band, tempo band,
   ruler) and the track-list header stay pinned.** This satisfies both
   documents on the stricter reading. Flagged rather than decided silently.
2. **Track count 20.** The plan does not specify a count for Arrange. 20 was
   chosen to match the Console channel bank so both rooms describe the same
   placeholder session, and because 20 rows genuinely overflow the visible area
   at both review widths, which is what makes the vertical-scroll check
   meaningful. Single constant (`ARRANGE_TRACK_COUNT`) and trivially reversible.
3. **56 bars / structure spans.** Placeholder geometry; the plan names the
   markers but not their lengths. Recorded in `src/lib/arrange.ts`.
4. **`--arrange-chrome-height: 13.75rem`.** A measured constant for the shell
   chrome above the room (app header + room header + paddings), used to bound
   the room height. It is deliberately slightly conservative: if chrome height
   changes the room ends a few pixels early rather than forcing a page scroll.
   Revisit if the app chrome changes.

### Remaining defects found on review

None that breach a Task 0.4 requirement. Three observations, all by design:

1. **Partially visible row at the top edge while scrolled.** The row that is
   half-scrolled past the sticky header shows its lower half (Track 03 at

   it is declared; needs re-measuring only if the shell chrome changes.
