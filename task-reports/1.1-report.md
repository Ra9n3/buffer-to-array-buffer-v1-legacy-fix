## How each hardware-reference requirement is met — technique by technique

The task asks for the specific technique, not a claim that the page looks
vintage. Nothing below applies the hardware look to the product UI; these
describe how the *token* represents it, so later component tasks have something
correct to consume.

**Warm near-black and dark grey-green surfaces (plan §4).**
`--al-material-panel: #23211d` is a brown-leaning black, not neutral — the "warm"
in the plan's "warm near-black" is why the red channel leads the blue.
`--al-material-surface: #2c2f2a` carries green over blue, giving the grey-green
module bay. `--al-material-surface-raised: #3a3d36` sits one step lighter so a
bevel edge has a value to read against rather than an outline on flat fill.
`--al-material-recess: #171614` is darker than the panel, because a recess is in
shadow.

**Walnut trim (plan §4).** `--al-material-wood: #5a3a26` — red-brown at low
saturation. Deliberately not orange, so it does not read as the orange functional
family or the accent stripe.

**Cream meter faces and incandescent glow (plan §4, spec §4a).**
`--al-material-cream: #e7ddc4`. `--al-material-lamp: #edb268` is *inside* the
spec's stated range `#e8a454`–`#f0c27a`; `check:tokens` parses both ends of that
range and fails if the lamp token falls outside it. The token encodes the colour
only — the soft bloom the spec demands is a rendering requirement for the meter
component in Task 1.5, and no glow is drawn here.

**Engraved lettering versus readable text (plan §4).** These are separate token
groups, not one ramp. Engraving is expressed as a *pair*:
`--al-text-engraved: #16150f` (the dark fill) plus
`--al-text-engraved-highlight: #4a4d45` (the 1px lighter cut edge used as an
offset shadow). One without the other reads as printed, not machined — which is
why they are two tokens and why the check asserts both exist.
`--al-font-label` is a condensed industrial stack; `--al-font-ui` is a readable
system stack; `--al-font-mono` handles tabular numbers, because a condensed sans
cannot align digits in a column.

**Functional colours (plan §4, spec §5).** Six families, each with its plan
meaning stored as data and printed on the playground. Each family carries
`base`/`hi`/`lo`/`ink`, so the two-part knurled knob with a radial-shaded cap
described in spec §1 can be built from tokens without inventing shades at
component level. Every `ink` value was chosen per family for contrast against its
own `base`.

**Organisational colours (plan §5b, spec §7).** Nine entries — eight swatches plus
`--al-org-neutral` — inside the plan's 24 cap. The registry text states they are
identity markers and never control colours, matching spec §7's instruction not to
wash a strip in organisational colour.

**Dense spacing (plan §4 "usable data density").** The scale is fine at the
control end (2/4/6/8px) and roomy at the page end (24/32/48px), declared in px so
panel dimensions do not rescale with the user's text-size setting.

**Independent inspectability.** Each token is its own card carrying four things:
the CSS custom property name, the live computed value, a plain-language purpose,
and its provenance (`Plan §4` / `Spec §5` / `Spec §4a` / `Plan §5b`). Colour
swatches are 56px blocks on a mid-grey sheet so neither light nor dark tokens are
flattered by their surround. Spacing tokens render an actual bar at that size
(capped so the 48px step still fits a card) next to the px value. Typography
tokens render real specimen text — the family itself, the size at that size, the
weight at that weight, two lines at that line height, a caps label at that
tracking.

## How the playground avoids a second source of values

Nothing on the page hard-codes a value:

- Every specimen draws with `style:background="var(--token)"` or
  `style:font-family="var(--token)"` and so on — the browser resolves it.
- The numeric value beside each specimen comes from `readTokenValues()`, which
  reads `getComputedStyle(document.documentElement)` for every registered token
  after mount. The 86 value fields were confirmed non-empty in the browser at all
  three viewports.
- Categories, families and role order all come from `tokens.ts` `TOKENS` and
  `TOKEN_CATEGORIES`, not from lists written into the page.
- `check:tokens` fails if either the stylesheet or the registry gains a token the
  other lacks, if a value-looking literal appears in the registry, or if any
  `font-size` on the page is a raw number rather than a token.

## Deviations, with reasons

1. **Values adopted from the project's earlier palette.** The plan and hardware
   spec name materials and colour families but supply only one numeric anchor
   (the lamp range). Rather than invent values, the six functional families and
   their `base`/`hi`/`lo`/`ink` roles were taken from
   `archive/documentation-site/lib/colors.ts`, the project's own prior palette.
   Panel, text and border values were derived around those anchors. Recorded as
   D1.1.1 in `decisions-log.md`.

2. **The route is `#/dev/components`, not `/dev/components`.** The app is
   hash-routed by locked Phase 0 decision. A literal path would break static
   hosting or require changing routing for every route. Recorded as D1.1.2.

3. **`decisions-log.md` was created rather than updated.** Plan §18 expects it;
   it did not exist. It records Task 1.1 decisions only and says so explicitly
   instead of inventing Phase 0 history.

4. **`architecture.md` was not created.** The task says to read it "if present"
   and does not ask for it. Not invented.

5. **`RoomNav.svelte` was modified.** It is not a room component, but it needed
   to accept `null` so the dev page does not claim a room. Its rendering is
   unchanged and `check:transport` still enforces the Task 0.5 nav rules.

6. **`main.ts` now imports `tokens.css`.** Required to make the tokens available
   to the page. The file declares custom properties only, so this cannot restyle
   anything — verified by `check:tokens`, which fails if `var(--al-` appears in
   any room source.

## Unresolved design choices and known issues

1. **No condensed label face is guaranteed.** `--al-font-label` resolves to a
   condensed face only where one is installed. If the engraved label must look
   identical on every machine, a font file has to be vendored into the repo —
   a dependency decision I have deliberately not taken. **Owner input wanted.**

2. **The playground scrolls.** It is a long reference page, so page scrolling is
   intentional there, unlike the three rooms. The mini transport stays fixed over
   it.

3. **Tokens are globally declared but deliberately unapplied.** They exist on
   `:root` for every page but no room references them; skinning is Phase 2.

4. **The three stray Phase 1 reports** described in the prerequisite section are
   still in the tree, unmodified, and contradict reality. Flagged for the owner.

5. **Grey-green is a judgement.** `#2c2f2a` reads green-grey but rests on a very
   small green lead over blue. It looks right on the swatch; it may want a nudge
   once real panels are built in Phase 2.
