## Summary

A single reusable `MiniTransport` component is rendered **once**, by
`App.svelte`, outside the room switch. It sits fixed at the bottom of the
application shell, beneath the active room, so it cannot be remounted, moved or
scrolled away by anything a room does.

It contains Previous / Play / Stop / Next buttons, a position/time readout
placeholder, a status placeholder, and a visible line stating that the controls
are placeholders and that no audio engine is connected. All controls are inert.

Completing this task required two consequences to be handled honestly, both
recorded under "Deviations":

1. The Console's own scroll-revealed transport placeholder was **removed**. It
   would have duplicated the shared strip, and it only appeared when the page
   was scrolled — which is now impossible, since the room no longer scrolls.
2. All three rooms are now **bounded to the viewport**. Arrange previously let
   the page scroll; with a fixed strip that left the transport sitting over the
   middle of the timeline, so the shell is now bounded there too.

No audio, playback, project state, DSP, routing, keyboard shortcuts, Phase 1
visual skin, or new dependencies were added. Tasks 0.1–0.5 results are
preserved.

## How the transport is shared across rooms

```
App.svelte
└── .app-shell
    ├── .app-header          ALLOY            Arrange | Console | Mixer
    ├── .room-host           {#if room === …}  ← the only thing that changes
    └── <MiniTransport />    ← rendered once, outside the {#if}
```

Because the component sits outside the room switch, switching rooms replaces
only the sibling above it. The transport's DOM node is never destroyed or
recreated — confirmed in the browser by holding a reference to the node across
six room switches and asserting it is still the live node each time
(`sameTransportNode: true`, `sameShell: true` on every switch).

No room renders a transport of its own; `check:transport` fails if any room
imports `MiniTransport` or emits a `data-transport-control`.

## How position and size are kept consistent

- The strip is `position: fixed; bottom: 0` across the full viewport width, so
  its position is independent of every room's internal layout and does not
  depend on the document's scroll position.
- Its height is declared **once**, as `--mini-transport-height: 2.75rem`
  (44px) in `app.css`; the component uses the token, and `.app-shell` applies
  `padding-bottom: var(--mini-transport-height)`. The shell therefore reserves
  exactly the space the strip occupies, which is what stops room content from
  ending up underneath it. A token rather than a literal in two places means the
  two cannot drift apart.
- At ≤30rem viewport width the token drops to 2.5rem (40px) so the bar stays
  proportionate on a small screen.
- The strip is a single non-wrapping flex row. As the viewport narrows, content
  gives way in a fixed order instead of clipping: the honesty note first
  (≤72rem), then the status readout (≤60rem), then the section label (≤48rem).
  The four controls and the position readout survive at every width tested,
  down to 480px.

## Placeholder behaviour

- Controls: `Previous`, `Play`, `Stop`, `Next` — real `<button type="button">`
  elements so they are keyboard reachable and inspectable. They are **inert**:
  no `onclick` handler exists, and they are deliberately *not* `disabled`, since
  a disabled control cannot be tabbed to and this is a structural review.
- Play is emphasised in grey as the future primary action. It is explicitly not
  the MIX button (that is a Console control, plan §2.3) and is not styled as a
  final control.
- Readout: `Position / time` with `00:00:00.000` in monospace.
- Status: `Idle — placeholder`.
- Honesty: visible text reads *"Placeholder controls. No audio engine is
  connected in Phase 0, so nothing plays."* Each button carries
  `aria-describedby="mini-transport-note"` pointing at that sentence, so the
  placeholder nature is available to screen-reader users too.
- No local "playing" demo state was added: the prompt allowed it only if needed
  to verify visual interaction, and it was not needed — hover and focus states
  were verified without implying playback.

## Deviations, decisions, and open items for owner input

1. **Console's transport zone removed.** The Console had a fixed panel that
   slid up once `window.scrollY > 24`. That mechanism is now dead — the Console
   room no longer scrolls — and a second transport placeholder underneath the
   shared strip would be a duplicate implementation, which this task explicitly
   forbids. The Console's full vintage transport, status/time display and MIX
   button remain scheduled as **Task 2.3**. This supersedes the Task 0.2 zone
   list; flagging it clearly because Task 0.2's report records three Console
   zones.

2. **Page-level scrolling removed from all three rooms.** Required by this
   task's own criterion ("room content must occupy the remaining available space
   without forcing unnecessary page-level scrolling") and by the non-overlap
   criterion. The consequence is that any future room content taller than the
   viewport must scroll **inside its own pane** rather than the page. Both
   current rooms already do this.

3. **MIX button not added.** The prompt's diagram shows only transport
   controls. MIX is a Console control per plan §2.3/§2.4 and is deliberately
   absent.

4. **No record/tempo/loop controls.** Not in the prompt's diagram and inventing
   them would exceed scope; the diagram says it communicates structure, not a
   requirement to add every optional control.

5. **Still no `decisions-log.md` or `architecture.md`.** Plan §18 expects both.
   Nothing this task decided needs to be deferred-and-recorded, so nothing was
   written — but if you want the deferred choices tracked in a `decisions-log.md`
   going forward, say so and I'll create one capturing the Phase 0 decisions
   retroactively rather than inventing history.
