## 2. The three reversals (owner decisions, not drift)

Each of these changed an instruction that a guard was built to protect. They are recorded as
**D9.2.1** rather than silently relaxed.

### 2.1 Home was the wordmark; it is now the fourth tab

`App.svelte` carried:

```svelte
<!-- The wordmark is the way Home (Task 4.1, owner D4.1.3). -->
<a class="app-brand" href={HOME_HREF}>ALLOY</a>
```

Home is **not** one of the three rooms, so deleting the wordmark as instructed would have deleted the
only route to Home — the route that `Start empty` lives on. This was raised before implementing, and
the owner chose **a fourth navigation tab**.

Home is a nav destination but **not** a `RoomId`:

```ts
export type RoomId = "console" | "arrange" | "mixer";   // unchanged
```

A room is a workspace with a transport-bearing canvas; Home is a screen of recent projects.
Promoting it would have rippled into room rendering, `data-active-room`, hrefs and every guard that
assumes three rooms. The tab is marked current from the route kind (`onHome`), so it behaves like a
tab without pretending to be a room.

### 2.2 Undo / redo / save were forbidden in the UI

`check-editing` asserted:

> no visible undo / redo / copy / paste / autosave control or text anywhere in the UI
> (owner: shortcuts only, store / API only, no settings UI)

The owner then asked for exactly those buttons. The check is **rewritten, not deleted**, and its real
concern is preserved and tightened: the clipboard must still be invisible, and the toolbar must bind
to the **one** project history and the **one** autosave rather than opening state of its own.

### 2.3 The Arrange band was pinned as the first thing in the room

`check-audio-import` asserted the band led the room. The owner ordered it removed. The check inverts,
and the invariant it protected is **strengthened**: exactly one file picker in the app, still the
platform's input, still `multiple` and WAV-only, and every entry point reaches that one input.

## 3. Save means something

The app saves itself — a debounced autosave after every edit. A Save button that only looked like a
Save button would be inert, so the toolbar's Save **flushes the pending write immediately** and
reports the outcome, including:

> Not saved — storage unavailable

when there is no storage. `Ctrl/Cmd+S` does the same. This was raised as a design question before
building; it is the only meaning a Save key can have in an auto-saving application.

---

## 4. Import: one picker, three doors

The picker moved out of Arrange into the shell:

- `AppToolbar` → **Import stems**
- `MenuBar` → `File > Import stems…`
- `Ctrl/Cmd+I`

All three call one `requestImport()`, which drives one hidden `<input type="file">` in `App.svelte`.
The old band's per-room input and its per-file report are gone; a failed batch is reported by the
shell instead. Importing from any room still imports into the open project.

## 5. "Final design assets" — not possible as written

The instruction asked to "replace all skeleton or placeholder UI elements with the final design
assets from the repo". **There are no design assets in this repository.** A full search found no
`.svg`, `.png`, `.webp` or `.jpg` outside the task-report evidence screenshots — no icon set, no asset
directory, no image library.

The design system here *is* code: `src/lib/tokens.css`, `src/lib/tokens.ts` and the hand-built
hardware components (`Lamp`, `Knob`, `Switch`, `EngravedLabel`, `MixButton`). The cream key caps, the
meter faces and the recessed wells are all drawn in CSS, not bitmaps.

The new menu bar and toolbar were therefore built **in that existing language** — the same neutral
greys, the same 1 px borders, the same darker cap the Play key uses for the primary action. No new
palette was introduced, and no placeholder whites were added. **If actual asset files exist, they need
to be uploaded**; nothing in the repo can be wired in because nothing is there.

## 8. Known gaps and deliberate omissions

- **Menu items deliberately absent.** No New / Open / Save-As / Export row: projects are created and
  reopened from Home, saving is automatic, and export has no UI yet. Printing disabled rows would
  advertise what the app cannot do. Documented rather than faked.
- **The Arrange import *report* is gone.** The band listed one line per file ("ADDED", "REFUSED",
  "UNREADABLE") and a per-file summary. Importing now reports only a failed batch. **Accepted
  silently-worse behaviour**: a user importing twelve stems and having two refused will no longer be
  told which two. This deserves a follow-up in the shell's import path.
- **`Cmd`/`Ctrl` in menu labels.** The shortcut hints are printed as `⌘I` / `⌘S`, which is
  macOS-style; the handler accepts either modifier. On Windows the hint is technically wrong.
- **The 9.1.4 sync guard never reached `main`.** `scripts/git-sync-guard.mjs` was committed on the
  previous session branch, which merged *before* that commit existed, so `main` does not have it and
  this branch does not either. It is worth re-landing separately.

## 10. Task 9.3 — the chrome is hardware (owner's review of §1–9)

The owner reviewed the first pass and rejected its material, correctly:

> "these should be a proper buttons like the whole other buttons in the app, find every button
> across the whole tabs that looks like this and make it like the rest of the tactile buttons"
> "all the grey areas should be the same as the area painted green, the whole app, the whole tabs
> should look like a hardware"
> "the menus should be on the left, the whole toolbar or upper bar must be, starting from the left,
> menus => tools buttons => tabs buttons, the bar should be thin … and it should be the same across
> the three tabs"

9.2 had built grey web buttons on a grey bar next to a hardware console. That was wrong, and the
whole premise of the product — plan §4, the hardware reference spec — is that this looks like a
machine.

### What changed

| Owner's point | Fix |
| --- | --- |
| Buttons are not tactile | New `ToolbarKey.svelte`: the approved cream cap from `TactileSwitch` variant A, **value for value** — same 135° ramp, edge lights/shades, specular bloom, wall and foot, same sinking press. Used by the menus, the toolbar, the listening source and the transport keys. |
| Every button, every tab | Tabs draw the identical cap in `RoomNav` (they must stay `<a>`). Checked every remaining raw `<button>` in shipping code: hardware already, or an invisible hit area. |
| Grey areas should be the green area | New `ChromeBand.svelte`: one material for the top bar *and* the transport strip — warm near-black plate, lit top bevel, shaded bottom bevel, brushing, walnut cheeks, from the shared tokens. The page ground moved from `#e4e4e4` to `--al-material-recess`. Every near-white surface in shipping code was converted. |
| Bar layout | One row inside the band: **menus → tools → tabs**, tabs pushed right, thin `0.375rem` padding. Same bar in all three rooms (drawn once, outside the room host). |
