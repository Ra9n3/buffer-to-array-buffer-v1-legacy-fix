## 1. What was built

An engine-only bounded renderer in `src/lib/engine/render.ts`:

```text
seekable RenderSource(s)
        │  bounded frame-range reads
        ▼
reused stereo input buffers ──► one MixEngine for the whole attempt
                                 │  existing 7.1–7.3 signal path
                                 ▼
                         raw bounded output
                                 │  drop limiter head latency
                                 │  stage aligned chunks
                                 ▼
                            RenderSink.write
                                 │
                    finish(result) = commit
                    abort(error)   = discard partial output
```

It supports long projects without accumulating full stems or a full output mix in the
renderer. It preserves the existing engine's processor state across chunk boundaries,
renders Return tails after the last input, compensates the master limiter's documented
lookahead, and recovers by aborting partial output and restarting cleanly.

No production render/export path existed before this task, so there was no UI or export
dialog to modify. The integration point is the engine API plus a WAV source adapter that
reuses the approved import/analysis readers. A later transport/export task can attach a
durable sink and controls without changing this rendering contract.

## 3. Chunk-size choice and memory behavior

- Default: `DEFAULT_RENDER_CHUNK_FRAMES = 4096`, the engine's existing block default
  (about 85.3 ms at 48 kHz).
- Configurable: whole-number `chunkFrames` from 1 to `MAX_RENDER_CHUNK_FRAMES = 65536`
  (about 1.37 s at 48 kHz). The cap is a provisional orchestration safety bound, not a
  DSP parameter or genre rule.
- The renderer allocates input buffers per track, one raw engine-output pair, and one
  aligned output staging pair from `chunkFrames`. The engine's existing scratch, bus,
  Return, master and sidechain key buffers are also sized from that block capacity.
- Source reads are frame-range reads into reused targets. Output is delivered to the
  sink chunk by chunk; the renderer never concatenates the output mix.
- DSP state remains sized by the approved module settings (delay time, reverb network,
  limiter lookahead), exactly as before. Duration increases the number of chunks, not
  the audio-buffer size.

Objective allocation test: with the same project and `chunkFrames = 4096`, a 0.5 s input
and a 4 s input both constructed **12 Float32 arrays totaling 49,152 elements**, with a
largest single Float32 allocation of **4096 elements**. The short render produced 9 sink
chunks; the long render produced 50. Audio allocation was identical.

## 4. State continuity

One `MixEngine` is constructed per attempt and reused for every block. There is no
reset, rebuild, parameter re-resolution or masking rerun at a chunk boundary.

Preserved across boundaries:

- EQ and Dynamic EQ filter state, detectors, envelopes and gain-design state;
- compressor and expander detectors/envelopes, including Auto Release state;
- bus processing and source-first bus order;
- sidechain key alignment: each block's keys are filled from that block's inputs before
  chains run;
- delay lines, damping state, reverb FDN/diffuser/pre-delay/early-reflection state;
- master limiter lookahead schedule, delay line and gain envelope.

Task 7.3 masking is supplied as an already-resolved project plus `maskingDynamicBands`.
The renderer passes those overlays and sidechain edges to the engine once and does not
recompute masking per chunk.

## 5. Tails and latency compensation

Let:

- `N` = longest input frame count;
- `T` = `ceil(tailSeconds × sampleRate)`, defaulting to `MixEngine.tailSeconds`;
- `L` = `MixEngine.latencyFrames` (the master limiter's reported lookahead).

The renderer processes `N + T` frames through the full engine. After `N`, inputs are
silence, so Return tails and detector releases advance through the same signal path.
`MixEngine.flush` drains the limiter's lookahead; it is not used as a shortcut for
Return tails.

The first `L` raw output frames are dropped and exactly `L` flushed frames are appended.
The delivered timeline is therefore `N + T` frames, aligned with the input, with the
limiter's residual audio preserved rather than zeroed or blindly trimmed. This follows
the compensation contract already recorded in `data-model.md` §15.6.

## 6. Recovery, cancellation and retry

- Cancellation is cooperative through `AbortSignal`, checked before/after source reads,
  engine blocks, sink writes and yields, and before commit. It throws
  `RenderCancelledError`.
- The project is fingerprinted at attempt start and re-checked before each engine block,
  after sink writes, and before commit. An observed project change throws
  `RenderProjectChangedError`, aborts the sink, and never calls `finish`.
- `RenderSink.finish(result)` is the single commit point. It is called only after all
  chunks and cleanup succeed.
- On cancellation or failure, `RenderSink.abort(error)` is called once and `finish` is
  not called. The sink owns durable/atomic storage; the renderer owns no files.
- Cleanup resets the engine, zeroes scratch/input/output buffers, and closes each unique
  source. A failed close/reset aborts the destination instead of reporting success.
- A retry is a new `renderProject` call with a fresh engine and fresh scratch buffers.
  No attempt state is shared. Source contracts are seekable so a clean restart can read
  from frame 0 again.

This task implements **safe restart**, not persisted mid-render checkpoint resume. That
is the plan's permitted alternative and avoids serializing every DSP module's internal
state or changing the project/persistence schema.

12. WAV stereo/mono decoding, mono duplication, damaged-float rejection, closed-source
    rejection;
13. named configuration/source mismatches;
14. monotonic, bounded progress ending at the delivered frame count;
15. tiny and non-divisible partitions (1, 7, 64, 999 frames) against continuous output;
16. short source reads and failed cleanup close abort instead of committing;
17. focused: a project change during a render aborts before commit and a stable retry succeeds.

**Comparison method.** A test-only continuous reference runs the same `MixEngine` in one
block, flushes the limiter, and applies the same head-drop/tail-append timeline. The
streaming renderer is compared sample-by-sample on both channels.

**Tolerance.** Tests require maximum absolute sample error and relative RMS error
≤ **1e-6**. The stateful block-invariance cases assert **exact equality (0 error)**:
the approved DSP updates state per sample and has no block-boundary branch, so chunking
should not change the arithmetic. The 1e-6 bound is a justified Float32 round-off guard
for comparisons, not permission for an audible seam. In the reported continuous-reference
tests the measured maximum error was **0**.

## 10. Deviations and findings

1. **No existing production render/export path.** The task therefore adds the engine
   rendering contract and source/sink adapters only. No UI requirement was discovered;
   none was added.
2. **`MixEngine.flush` is limiter-only in the current implementation.** Return tails are
   rendered by processing silence through the full engine before the limiter flush.
   This preserves the approved signal path instead of changing DSP or pretending a
   limiter flush drains a reverb network.
3. **Recovery-only engine edit.** `MixEngine.reset()` now clears scratch and sidechain key
   buffers as well as processors/accumulators. The next block already overwrote keys, so
   this does not change rendered sound; it removes stale samples after reset/failure.
4. **Safe restart instead of persisted checkpoint resume.** The plan allows interrupted
   renders to resume or safely restart. Persisted DSP checkpoints would require new
   serialization contracts outside this task.

## 11. Limitations and remaining work

- The project is contractually read-only during an attempt, and a controller that edits
  it should still cancel and start a new render. The renderer now fingerprints project
  metadata and aborts before commit if it observes a change; no project snapshot/schema
  was added. A change that is made and fully reverted between checks may be invisible,
  but the engine only reads project state synchronously at checked block boundaries.
- Inputs use the current bar-1 imported-stem model. Arrangement clip offsets, automation
  and section-driven parameter changes are not introduced here.
- Cancellation is cooperative at chunk/read/write boundaries; an underlying source read
  is not forcibly interrupted unless its own implementation supports that.
- The sink owns atomic durable storage and any user-facing retry/resume UI. WAV export,
  processed stems/buses and export dialogs remain Task 8.2 work.
- Tail length is the approved conservative Return contract; an override can shorten it,
  and a long tail may include very low residual energy before the final limiter flush.
- No true-peak limiting, mastering, loudness target, native code or new dependency.

## 12. Focused verification: project changes during a render (2026-11-04)

**Question.** Does the rendering API detect project changes during an attempt and
prevent committing inconsistent output?

**Finding before the safeguard.** The caller contract said the project must remain
stable, but the API did not enforce or observe that. `MixEngine` caches most chain
settings at construction, yet it reads some routing/send state from the project during
blocks, so a mid-render edit could produce output that no longer matched either the
starting project or the final project. The contract alone was not a guarantee.

**Smallest safeguard added.** `renderProject` now takes a deterministic metadata
fingerprint of the project at attempt start (`JSON.stringify` with functions omitted)
and re-checks it:

- before each engine block, after async source reads;
- after each sink write, before more output is produced;
- before `sink.finish`, after cleanup.

An observed change throws `RenderProjectChangedError`. The normal failure path resets
the engine, closes sources, zeroes scratch buffers, and calls `sink.abort`; `finish` is
not called. The fingerprint is project-metadata sized, not audio sized, and does not
change the bounded audio-allocation contract.

**Focused test.** `tests/rendering.test.mjs` — “a project change during a render aborts
before commit and a stable retry succeeds”. A send level is mutated after the first
sink write. The attempt rejects with `RenderProjectChangedError`, the sink records an
abort and no finish, and a fresh retry against the stable project commits and matches
the continuous reference exactly.

**Boundary semantics.** JavaScript engine blocks are synchronous, so the project cannot
mutate inside a block. Checks surround the async boundaries where a caller can edit.
A transient edit that is fully reverted before the next check may be invisible; if no
checked engine block observed it, the rendered output remains consistent with the
fingerprinted project. Persistent edits are caught before they can affect another block
or commit.
