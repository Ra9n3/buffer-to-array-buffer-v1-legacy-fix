## Implementation summary

**One engine.** Every module converts level to dB the same way, links channels the
same way, smooths with the same one-pole and uses the same quadratic knee
(`src/lib/dsp/dynamics.ts`). Three copies of "what a decibel is" would be three sets
of bugs; a shared engine is also what makes the four characters genuinely one
compressor with four behaviours rather than four compressors.

**The compressor** is one `process` loop over one envelope. A character selects the
detector (`peak` or `rms`), the knee (0 / 3 / 9 / 12 dB), a progressive-ratio factor
and span, and — when Auto Release is ON — a release law. The five controls are
D2.8.3's exactly (THRESH −40 … 0, RATIO 1 … 20, ATTACK 0.1–100 ms, RELEASE
10–1000 ms, MAKEUP 0 … +20). Make-up is applied as `10^((makeup − reduction)/20)`,
with unity exact when both are zero.

**The expander** is the same knee evaluated below the threshold, clamped to RANGE.
ATTACK is the opening time — attenuation removed as the level rises — and RELEASE is
the closing time — attenuation added as the level falls — which is the reverse of
the compressor's intuition and is stated in the code where it happens.

**The limiter** is a sample-peak brickwall with a 5 ms lookahead. The delay line is
exactly `latencyFrames` long; a sample over the ceiling needs `ceiling/peak` at the
frame it is due out, so the module ramps its scheduled gain down to that target
across the lookahead and every sample still in flight already accounts for it. The
applied gain is `min(scheduled, release-recovered)`, so the release can never undo a
scheduled reduction. `flush` drains the line so the tail is written, not cut.

## Important DSP decisions and rationale

**Provisional numbers, each in one constant.** No document fixes any of these, so
each lives in exactly one place (`params.ts` or the character table) and is marked
PROVISIONAL:

| decision | value | why this value |
| --- | --- | --- |
| compressor knee widths | 0 / 3 / 9 / 12 dB | a spread wide enough to be audible at low over-threshold levels; 0 gives the "bites at the threshold" character |
| progressive factors / spans | 1.5 @ 40 dB · 2.5 @ 40 dB · 2.5 @ 60 dB | small enough that the curve's slope stays below 1 (checked by a monotonicity sweep) yet large enough to be measurable at 30 dB over |
| RMS window | 10 ms | long enough to read a body, short enough to follow a bar; the same 10 ms the dynamic EQ's meter smoothing uses |
| Auto Release laws | depth-slower / depth-faster / two-stage / two-stage-tail | four distinct, testable behaviours, one per character |
| expander threshold / ratio / range | −60…0 dBFS · 1…4 · 0…40 dB | the printed ratio list cut at 4:1 as the owner asked; 40 dB of range is enough for any cleanup and still leaves the signal present |
| expander knee | 6 dB, fixed | the owner's number; keeping it fixed holds the control count at five |
| limiter ceiling / release | −12…0 dBFS · 10–1000 ms | wide enough to be useful, narrow enough that a typo cannot produce silence or an audible pump |
| limiter default | −1 dBFS, 50 ms, 5 ms lookahead | the owner's safety margin, not a headroom policy; 50 ms is a transparent recovery; 5 ms is long enough for a ramp and short enough to stay latency-invisible |

**What the characters actually change — and what they do not.** Each character is a
detector, a knee and a ratio law. There is **no added saturation**: no tanh, no
clipper, no transformer model, no tube, no optical cell. The plan's rule ("no added
saturation") is a constraint, not a limitation to work around, and the guard fails
if any of it appears. The characters are **topology-inspired**, never sold as
emulations (D2.8.1).

**The knee's direction, stated precisely.** The symmetric quadratic knee gives
*some* reduction below the threshold and meets the straight line at the knee's top
edge: at the threshold itself it reads `a·W/8` dB (0.84 dB for Opto's 9 dB knee).
So a wide knee starts earlier and more gradually; it is not "less compression"
above the knee. The suite asserts the curve, the edges and the convergence at the
top edge, because the alternative reading ("a soft knee lets more through") is a
common and wrong description.

**The progressive ratio is bounded by construction.** The ratio walks from the
knob's value toward `1 + (ratio−1)·factor`, capped at 20:1, covering half of the
remaining distance every `span` dB past 10 dB over the threshold. The target scales
the *distance above unity*, not the ratio, so **1:1 is exactly neutral for every
character** — an early version scaled the ratio itself and made a 1:1 setting
compress at high drive; the monotonicity and neutrality tests are why that was
caught before the report.

**What ATTACK, RELEASE and RATIO mean per character.** ATTACK and RELEASE are
one-pole time constants on the **level envelope in dB**, measured to 63.2 % of a
step (the suite steps across the threshold so the reduction and the envelope travel
the same distance). RATIO is exact up to 10 dB over the threshold; above it VCA
walks to 1.5×, FET and Vari-Mu to 2.5×, and Opto stays static. Those three
sentences are the readouts' definitions, and §15.2–15.3 of `data-model.md` record
them.

**Linking.** One gain envelope per module, from the greater channel's level, applied
to both: peak characters link peaks, RMS characters link RMS (forcing peak on an
RMS character would erase it), the expander and limiter link `max(|L|, |R|)`.
Never a sum — a correlated centre would over-trigger — and never per-channel. No
user-facing link control.

**Latency, honestly.** `latencyFrames = round(5 ms × rate)` (240 at 48 kHz, 221 at
44.1 kHz) and it is the module's actual delay: the ring is exactly that long. A
renderer drops that many leading frames and calls `flush`, so the take keeps its
length without blind trimming. Bypassed, the limiter still delays — toggling it
never moves a render's alignment.

## Deviations, limitations and approval items

1. **Auto Release is not in any document.** It is implemented as the owner
   described, defaulted OFF, and documented in §15.4 as new. If the project later
   logs it, the log entry is the owner's.
2. **All character and limiter constants are provisional.** Knee widths, progressive
   factors and spans, the RMS window, the Auto Release laws, the expander's
   THRESHOLD / RATIO / RANGE, the limiter's ceiling range / default and release
   range, and the 5 ms lookahead are this task's app-design choices. Each is one
   constant; a later tuning task moves them in one place.
3. **Knee width behaves as the quadratic knee does**: slightly *more* reduction
   just around the threshold for wider knees, converging at the knee's top. That is
   the standard shape, and it is what the tests assert; it is worth knowing before
   anyone tunes the widths by ear.
4. **True-peak limiting is not here.** The ceiling is a sample-peak ceiling; inter-
   sample peaks can exceed it. A future version must verify the output, because 4×
   detection alone is not a limiter (D5.2.6's analyser is a measurement).
5. **No lookahead for the compressor or the expander.** Their attack is a one-pole,
   so a sample faster than the attack is passed unattenuated, as in the classic
   topology. Nothing in the documents asks for lookahead there.
6. **The expander's cold start ducks** until its envelope rises from silence — the
   same behaviour the compressor has harmlessly and any gain-riding module has. It
   is documented and tested (the passthrough test measures the settled part).
7. **`latencyFrames` is the renderer's to honour.** This task reports it and
   provides `flush`; it does not compensate anything, because chunked rendering is
   Task 7.4's.
8. **Bundle and isolation unchanged**: nothing outside `src/lib/dsp/` imports the
   modules and the guard enforces it.

Nothing above blocks approval; each is a place where a future tuning or wiring task
has a decision to make with the numbers in front of it.
