## 4. Implementation summary

### 4.1 The channel chain

`TrackChain` runs the eight `PROCESSING_CHAIN_STEPS` in order and nothing else:
**trim → expander (only when `cleanup`) → static EQ → dynamic EQ → compressor → pan →
fader → sends/routing**. Each module is constructed once, from the model, and holds its
own state across blocks.

Three choices worth naming:

- **Trim is audio gain, not a detector offset.** It is step 01 of the plan, so it changes
  the level every later detector sees. That is the difference between a trim and a
  threshold, and the tests pin it (TRIM lifts the compressed output by exactly the trim).
- **Dynamic bands carry `gain: 0 dB` and only their depth.** The band's static gain
  already happened at step 03; giving the dynamic filter the same static gain would
  multiply a static and a dynamic setting twice. The band still *filters* at the same
  frequency and Q, which is what the dynamic detector needs.
- **A skipped path is frozen.** Muted, unsoloed or bypassed, a chain is not processed and
  not reset — the 6.1–6.3 bypass rule, extended to routing. This is what lets a mute
  release without a jump, and the test proves it against a fresh engine.

### 4.2 Pan and balance

`panGains()` is the approved constant-power law, with `cos(π/2) ≈ 6e-17` tidied to
exactly 0 so a hard pan is silent on the other side rather than "almost". `L² + R² = 1`
is asserted across the range, and hard positions are unity.

`balanceGains()` is deliberately a different function. The owner's answer said BALANCE
uses the pan law "on a stereo pair"; applied literally, a bus at its **default** centre
position would lose 3.01 dB — a gain the model does not hold, and a direct disagreement
with the same track routed straight to Master (0.707 vs 0.5). So BALANCE reads like a
console balance control and is documented in `data-model.md` §17.3: unity on both sides
at centre, linear attenuation of the opposite side when moved, never a boost. This is the
one place where I narrowed an approved answer, and §8.3 asks for confirmation.

### 4.3 Summing and routing

- Plain Float32 addition at every node; **no compensation for the number of contributors**.
- Buses are processed **sources first** (`busProcessingOrder()`), so a bus feeding a bus
  is finished before it is read, and the signal reaches Master exactly once.
- Sends are **post-fader and post-pan** (step 08), and a send at `−60 dB` is exactly zero.
- A Return's output is fixed to Master.
- The constructor runs `validateGraph()` first and **throws** with the verdict's reason
  (dangling bus, cycle, Return to a bus, send to a missing Return). Invalid graphs are a
  store bug, not a runtime condition to survive, so the engine does not skip or repair.

### 4.4 Bus and Return processing

`BusChain` is trim → EQ → compressor → balance → fader: no pan, no sends, no dynamic EQ —
a bus is not a channel (plan §7). `ReturnChain` is effect → level, wet only, with the
Return fader as its own level (`−60…0 dB`); there is no dry path to duplicate, so the
"no duplicate dry, no feedback" requirement is structural rather than defensive.

### 4.5 The Master and the lifecycle

The Master is the sum through the 6.2 safety limiter, always in circuit, with no fader.
Its 5 ms lookahead is the engine's `latencyFrames` (240 frames at 48 kHz) — reported, not
hidden, so 7.4 can compensate for it.

Processors and every buffer are allocated **once** in the constructor from
`maxFramesPerBlock` (default 4096); `process()` allocates nothing and treats a larger
block as a named error. `reset()` clears all state and accumulators. `flush()` runs the
tail out with no input. `tailSeconds` is the longest Return tail (3.93 s on the fixture
session, from the plate's pre-delay + decay).

`refreshAudibility()` re-reads mute and solo after a controller changes one, recomputing
only the pass/fail routing — no chain is rebuilt, no state is lost.

## 5. Important decisions and rationale

| Decision | Why |
| --- | --- |
| Master = unity sum + always-on limiter, no fader | The model has no Master entity; the owner's answer keeps the 6.2 limiter as the only protection and makes the engine's ceiling true by construction |
| Solo in place, mute wins | The plan's solo is a listening function, not a re-route: a soloed track keeps its bus, so what you hear is what the mix will be |
| Post-fader, post-pan sends | Step 08 is after 06 and 07 in the approved chain; a pre-fader send would contradict the ladder |
| Balance ≠ pan law | §17.3 and §8.3: a neutral default is a correctness requirement, not a taste |
| Throw on an invalid graph | Silently skipping a broken route hides a store bug behind silence |
| Character mappings throw on an unknown id | `CharacterId "varimu"` is not `CompressorCharacterId "vari-mu"`, and `ReturnCharacterId` spans both effects; explicit mapping functions name the offender instead of casting |

### 8.2 The delay was not safe in place — fixed, and this is a change to a 6.3 file

`buffers.ts` states that a module's output may be the same arrays as its input, and the
Return chain relies on it. `Delay.process()` read `input[c][i]` **after** writing
`output[c][i]`; with `output === input` the line fed itself its own output and produced
silence. The fix captures the source sample first:

```ts
const source = input[c][i];   // before the output write: in place is allowed
const read = buffer[at];
output[c][i] = scale * read;
buffer[at] = source + gain * filtered;
```

Behaviour with separate buffers is unchanged (all 12 original delay tests still pass,
now 13 with the new in-place equality test). **Approved at closeout (owner, 2026-11-03;
`decisions-log.md` D7.1.1): the fix stays in the reviewed module.** The alternative —
hiding the defect behind a scratch buffer in the engine — was rejected because it would
have left a latent trap for every later caller.

### 8.3 BALANCE narrows the approved pan law

§4.2: at the default centre, the pan law costs 3.01 dB, which a bus default must not.
BALANCE is unity-at-centre and attenuation-only. **Approved at closeout (owner,
2026-11-03; `decisions-log.md` D7.1.2): the implementation stays as built** — strict
identity with the pan law was considered and declined, because a bus would then be 3 dB
quieter than the same material sent straight to Master.

### 8.4 Provisional constants

Two gate values (dynamic EQ −24 dBFS / 5 ms / 120 ms; cleanup −45 dBFS / 2:1 / 20 dB /
5 / 120 ms) come from the owner's approval and are marked `PROVISIONAL` in
`constants.ts` and in `data-model.md` §17. They are calibration, not contract.

### 8.5 Limitations that belong to later tasks

- **No latency compensation.** The engine reports 240 frames; aligning rendered material
  against it is 7.4's job.
- **No chunked rendering or tail scheduling.** `tailSeconds` and `flush()` are the
  contract 7.4 will consume.
- **No sidechain and no masking** (7.2, 7.3): the compressor looks only at its own input.
- **No store or UI wiring.** The engine is constructed from a `Project`; who constructs
  it, and when, is a later task. The bundle is unchanged (§6.3).
- **Mute/solo changes need `refreshAudibility()`.** A controller that forgets it will
  hear the previous state. Worth pinning in the UI task.
