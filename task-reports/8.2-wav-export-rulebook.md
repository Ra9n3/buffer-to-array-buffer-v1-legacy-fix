## 2. Export behaviour

### 2.1 The three outputs

| selection | file | contents |
| --- | --- | --- |
| **Full mix** | `<Project> - mix.wav` | the complete path: every track's inserts → post-fader sends → Returns' effects → bus chains → summing → master safety limiter |
| **Processed stems** | `Stems/NN <Track>.wav` | one render per track: its inserts, its pan/fader, and its declared route (bus chain, or Master) |
| **Processed buses** | `Buses/NN <Bus>.wav` | each bus after its own chain, before it is summed into its destination |

Any combination may be selected. Mix and bus files come from **one pass** — the only place
where every bus's processed output exists — so they are consistent by construction and the
bus taps that feed Master sum exactly to the master signal before the safety limiter
(asserted).

### 2.2 How the taps work (the renderer change)

`RenderOptions.onBuses` hands the caller each bus's output for the block the engine just
processed. Buffers are allocated only when asked for; the callback is awaited, so a writer
applies backpressure exactly as the sink does. `startFrame` is the input frame of the block:
buses carry no latency and the master's limiter lookahead is compensated by the master's own
head drop. The delivered master is **bit-identical with and without the taps** — asserted.

### 2.3 Stems: what is in one, and what cannot be

A stem is rendered from a project containing **one track** and **only the Returns its live
sends reach**, with `sidechains: []`. So:

- its inserts, pan, fader, mute and solo apply — the stem agrees with the mix;
- its **bus chain applies**, because the route is part of the track's sound;
- its **own send and that Return's effect** are in it;
- therefore **the stems sum to the full mix** sample-for-sample over the project's length,
  with two documented exceptions: the master safety limiter is a sum-level overs guard and
  is not in any stem, and a Return is shared, so its wet signal reaches the mix once per
  contributing send.

Each stem's `export.json` entry says so in words:
`routing.output`, `routing.sends[{to, levelDb, inStem: false}]`, and a note naming the
Return to re-create and stating that the master limiter is absent. This is plan §12's
"document carefully when bus processing contributes to the sound", discharged in the folder
itself rather than in a manual.

### 2.4 Format, sample rate, and the absence of mastering

- **32-bit IEEE float WAV by default**, stereo, at the project's rate (`DSP_SAMPLE_RATE`,
  48 kHz). The written samples are the rendered samples **exactly** — the test's max sample
  error is `0`.
- **24-bit PCM** available as `formatFromId("pcm24", rate)`: rounds to nearest, clamps at
  full scale, and reports `clipped: true` per file rather than wrapping.
- **No dither, no noise shaping, no `-14 LUFS`, no normalisation, no maximisation, no
  master EQ/compression.** The safety limiter stays as §15/§16 fixed it — an overs guard.
  A quiet mix stays quiet (a −40 dB fader yields a peak under 0.01); a hot one is held at
  the ceiling rather than turned down to a target (`mastering: "none"` in the manifest).
- WAV only, as §12 requires.

### 2.5 Folder structure and names

```
<Project>/
  <Project> - mix.wav
  Stems/01 Kick.wav
  Buses/01 Drums.wav
  export.json
```

One pure module decides every name, in this order: strip what a file system cannot hold →
never lead with a dot, never end with a dot or space → escape DOS device names
(`CON` → `CON (name)`) → truncate to an **80-byte** budget with `…` (bytes, so a multi-byte
character is never split) → dedupe **case-insensitively** with ` (2)`, ` (3)`. Stem and bus
numbers come from the model's own `code`, so the files match the Console's strip order.

### 2.6 Progress and failure behaviour

`preparing → rendering → writing → manifest → done`, per file and overall, with the overall
fraction holding a high-water mark (never backwards). Nothing is thrown at the caller and no
half-written file is left behind:

| situation | behaviour |
| --- | --- |
| nothing selected | `stopped.reason = "no-selection"`, one sentence |
| the selection has nothing to render | `stopped.reason = "no-audio"` plus the plan's own note |
| one file fails | that file is **aborted** and recorded; the rest continue |
| the folder cannot be created | `reason = "write"`, the export stops |
| unsupported format/rate | `reason = "format"`, fatal (the next file would fail identically) |
| user cancels | `reason = "cancelled"` |
| project changed mid-export | `reason = "project-changed"` |
| a bus receives nothing | left out; `plan.notes` says how many |

Failures also land in `export.json` as `skipped`, so a folder cannot look complete when a
file is missing.

## 3. Rulebook behaviour

Schema `alloy.rulebook/1`; a file has `id`, `name`, and `targets` scoped to `all`, a
`family` or a `role`, each with `settings: [{parameter, value}]`.

- **The vocabulary is the engine's own `ParamSpec` objects, by identity** — `RULES["eq.lf.gain"].spec === EQ_GAIN`. A rulebook cannot invent a control, a unit or a range.
- **Locked decisions are refused by name** (`priority`, `tier`, `mode`, `ownership`,
  `routing`, `output`, `sends`, `master`).
- **Validation collects every problem** and never throws:
  `{ok:false, problems:[{kind, path, message}]}` with JSON paths. Kinds: `missing`,
  `malformed-json`, `unsupported-schema`, `structure`, `unsupported-parameter`,
  `pinned-parameter`, `value-out-of-range`, `wrong-type`.
- **Loading distinguishes "no such file" from "not JSON" from "written for a newer build"**,
  and `loadRulebooks` loads several while keeping each problem beside its file.
- **Application is the softest nudge**: only `auto` values are written (a Manual value is
  the user's), values are clamped and stepped to the spec, unmatched scopes are reported,
  the caller's project is untouched (copy-on-write), and applying twice changes nothing.
  It is documented as running **after** tier/priority and masking (plan §9's precedence).
- **The shipped rulebook is inert**: valid, empty, and self-explaining. **No genre-specific
  numeric value was invented or tuned**, which was an explicit constraint.

## 5. Decisions

Recorded in full in `decisions-log.md` under **Task 8.2**: D8.2.1 (no second pipeline; the
tap contract), D8.2.2 (a stem is a channel plus its route), D8.2.3 (float32 default, 24-bit
offered, no mastering), D8.2.4 (names, bytes, case-insensitive dedupe), D8.2.5 (rulebooks
against the engine's own specs, inert by default), D8.2.6 (test and guard strategy).

Two decisions worth surfacing here:

1. **A stem keeps its bus chain.** It makes the stem set sum to the mix, and it makes each
   stem *the track's sound* rather than a pre-bus intermediate. The cost — the bus chain is
   then duplicated across the stems and the bus file — is documented per stem.
2. **The tap does not subtract the limiter lookahead.** The first implementation did, and
   every bus file arrived 5 ms early; a test now cross-correlates bus against mix and
   requires a best lag of exactly 0.

## 6. Deviations and known limits

- **No UI.** The task is functional integration; the plan's export dialog and rulebook
  screen are not part of 8.2 and were not built. Loading a rulebook is a `readText`
  callback, so the module stays free of DOM and Node specifics. `data-model.md` §21.7 was
  updated: engine-level export is no longer deferred, the screen still is.
- **`architecture.md`, `module-contract.md` and `glossary.md` do not exist** in this
  repository (the prompt template lists them among the required reading). Nothing was
  invented for them; the decisions went into `decisions-log.md` and `data-model.md`.
- **`encodeWav` from `src/lib/audio/wav.ts` was not reused.** It is documented
  tests/evidence-only and needs the whole file in memory; `WavStreamWriter` streams a block
  at a time. Both are documented in D8.2.3.
- **A stem's length is its own signal plus its own Return tail**, so the "stems sum to the
  mix" assertion is made over the region every stem covers (the project's length). Past
  that only the Return tail continues, and only in the mix and in the files that send
  into it. This is the renderer's own tail rule, not an export choice.
- **The 4 pre-existing `bridge-fixtures.ts` type errors** (`LED_LADDER_SCALE`,
  `LedSegment`) remain untouched — they predate this task and are outside its scope.
  `npm run check` (svelte-check, the project's gate) reports 0 errors.
- A bus with no routing into it is skipped and counted in the notes, rather than written as
  a silent file.
